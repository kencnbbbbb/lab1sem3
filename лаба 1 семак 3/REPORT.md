# Лабораторная работа № 1
# Абстрактные структуры данных. Вариант 3

## 1. Цель и постановка задачи

Цель: изучить алгоритмы формирования абстрактных структур данных и выполнения операций над ними.

Реализовать массив, односвязный и двусвязный списки, стек, очередь, дерево Complete Binary Tree. Реализовать командный интерфейс, загрузку и сохранение данных. Проверить работу на различных входных данных, определить сложность операций, сравнить применение структур.

Основная реализация выполнена на C++17. Дополнительная реализация на Go поддерживает те же команды. ФИО, группа и реквизиты титульного листа в предоставленных данных отсутствуют, поэтому здесь приведена содержательная часть отчёта.

## 2. Организация программы

Программа запускается с параметрами `--file` и `--query`. Один запуск соответствует одному запросу. Перед выполнением запроса данные загружаются из текстового файла в именованные структуры. Затем проверяются команда, число аргументов, тип контейнера и допустимость индексов. После успешной изменяющей команды состояние записывается во временный файл, который заменяет основной файл.

Линейные структуры содержат строки без пробелов, дерево — целые 32-битные числа. Имена контейнеров уникальны среди всех типов. Для хранения таблиц имён C++ использует `std::map`, Go — встроенный `map`. Это служебные таблицы; массивы и списки реализованы отдельно, стек и очередь построены на списках. Для служебного обхода дерева используется очередь.

В C++ узлы и буфер массива выделяются динамически. После выполнения или ошибки программа освобождает память всех загруженных контейнеров. В Go освобождением недостижимых объектов управляет сборщик мусора. Структуры C++ с сырыми указателями не следует копировать как независимые владельцы: работа ведётся через ссылки на объекты в таблицах имён.

## 3. Алгоритмы

### 3.1. Динамический массив

Хранятся указатель на буфер, число элементов `size` и вместимость `cap`. Начальная вместимость — 16. При заполнении создаётся буфер удвоенной вместимости, элементы копируются, старый буфер освобождается. В C++ сохранён предел из примера — 65536 элементов.

Добавление в конец записывает значение в позицию `size` и увеличивает длину. Вставка по индексу сначала сдвигает суффикс вправо, удаление — влево. Чтение и замена обращаются к элементу по индексу. При вставке допустим индекс, равный длине; при чтении, удалении и замене он должен быть строго меньше длины.

### 3.2. Односвязный список

Узел содержит значение и ссылку `next`. Список хранит `head` и `tail`. Добавление в голову и хвост меняет постоянное число ссылок. Для удаления хвоста требуется найти предпоследний узел.

Операции перед/после значения сначала находят первое совпадение при движении от головы. Для вставки или удаления перед узлом сохраняется его предшественник; для удаления перед узлом может требоваться также предшественник удаляемого элемента. При удалении головы или хвоста обновляются граничные указатели.

Прямое чтение идёт по `next`. Обратное чтение сначала собирает значения во вспомогательный массив, затем выводит его с конца. Отсутствующий ключ и отсутствующий сосед не изменяют список.

### 3.3. Двусвязный список

Узел хранит значение, `next` и `prev`. Список хранит голову и хвост. Добавление и удаление на обоих концах выполняются изменением постоянного числа ссылок. Для операций относительно значения сначала выполняется линейный поиск первого совпадения, затем меняются ссылки соседних узлов.

Прямое чтение использует `next`, обратное — `prev`. Проверки пустого списка предотвращают обращение к отсутствующим голове и хвосту. При совпадении ключа в нескольких узлах применяется именно первый узел от головы.

### 3.4. Стек

Стек работает по принципу LIFO: последний добавленный элемент извлекается первым. В C++ он построен на голове односвязного списка: добавление и извлечение происходят в голове. В Go используется хвост двусвязного списка. Обе реализации дают O(1) на push/pop.

Чтение показывает вершину первой. Для сохранения в файл используется противоположный порядок — от основания к вершине. При загрузке последовательное добавление восстанавливает исходную вершину. Извлечение из пустого стека является ошибкой.

### 3.5. Очередь

Очередь работает по принципу FIFO: первым извлекается элемент, который добавлен раньше. Добавление производится в хвост, извлечение — из головы. Сохранение и чтение используют порядок от головы к хвосту. Извлечение из пустой очереди является ошибкой.

### 3.6. Complete Binary Tree — индивидуальный вариант 3

**Определение:** все уровни двоичного дерева, кроме, возможно, последнего, заполнены полностью; узлы последнего уровня занимают самые левые позиции без пропусков. Пустое дерево считается Complete.

Это условие определяет форму дерева. Оно не требует упорядочивания значений как у дерева поиска. Поэтому поиск произвольного значения имеет O(n), несмотря на логарифмическую высоту дерева. Повторяющиеся значения допускаются.

**Вставка:**

1. Если корня нет, новый узел становится корнем.
2. Поместить корень в очередь.
3. Извлекать узлы по порядку обхода в ширину.
4. Если левое поле свободно, поместить новый узел туда и закончить.
5. Иначе, если правое поле свободно, поместить новый узел туда и закончить.
6. Иначе добавить обоих детей в очередь и продолжить.

При условии, что дерево до вставки было Complete, новый узел занимает первую свободную позицию последнего уровня либо начинает следующий уровень. Следовательно, вставка сохраняет свойство Complete. Индукция по числу вставок доказывает корректность построения из пустого дерева.

**Поиск:** обход в ширину с последовательным сравнением значений; при совпадении вернуть `TRUE`, при исчерпании очереди — `FALSE`. Направление поиска не определяется сравнением значений, так как дерево не является деревом поиска.

**Проверка Complete:**

```text
поместить корень в очередь
пропуск = ложь
пока очередь не пуста:
    извлечь узел
    если узел отсутствует:
        пропуск = истина
    иначе:
        если пропуск: вернуть ложь
        добавить левого и правого ребёнка, включая отсутствующих
вернуть истина
```

Позиции рассматриваются по уровням слева направо. У Complete-дерева все занятые позиции идут до всех свободных. Если после свободной позиции встретилась занятая, имеется пропуск и дерево не Complete. Это одновременно объясняет необходимость и достаточность проверки.

**Чтение и сохранение:** обход в ширину. Повторная вставка сохранённой последовательности восстанавливает то же расположение значений в Complete-дереве. `PRINT` выводит пары «путь = значение», что позволяет однозначно восстановить связи.

Удаление из дерева заменено проверкой Complete согласно условию варианта. Балансировки и повороты не нужны.

## 4. Сложность операций

Обозначения: n — число элементов в выбранной структуре, k — число значений в одном запросе. Время сравнения и копирования одного значения условно считается O(1); для строк переменной длины нужно дополнительно учитывать их длины. Таблицы ниже описывают сами структуры, без чтения всего файла, записи и поиска имени контейнера.

### 4.1. Массив

| Операции | Время | Дополнительная память |
|---|---|---|
| `MCREATE` | O(1) при фиксированной начальной вместимости | O(1) |
| `MPUSH`, одно значение | O(1) амортизированно, O(n) при расширении | O(n) при расширении |
| `MPUSHIDX` | O(n) в худшем случае | O(n) при расширении, иначе O(1) |
| `MGET`, `MSETIDX` | O(1) | O(1) |
| `MDELIDX` | O(n) | O(1) |
| `MLENGTH` | O(1) | O(1) |
| `MREAD`, `PRINT` | O(n) | O(n) для строки вывода |

Удвоение вместимости даёт суммарно O(n) переносов при n последовательных добавлениях, поэтому добавление амортизированно O(1). Вставка и удаление в середине сдвигают до n элементов.

### 4.2. Списки

| Операции | Односвязный F | Двусвязный L |
|---|---|---|
| `XCREATE` | O(1) | O(1) |
| `XPUSH`, `XPUSHHEAD`, одно значение | O(1) | O(1) |
| `XPUSHBEFORE`, `XPUSHAFTER` по значению | O(n) | O(n) |
| `XPOPHEAD` | O(1) | O(1) |
| `XPOP` — удаление хвоста | O(n) | O(1) |
| `XPOPBEFORE`, `XPOPAFTER` по значению | O(n) | O(n) |
| `XDELVAL`, `XFINDVAL` | O(n) | O(n) |
| `XREADHT`, `XREADTH`, `PRINT` | O(n) | O(n) |

У двусвязного списка изменение ссылок около уже известного узла стоит O(1), но интерфейс принимает значение, поэтому предварительный поиск даёт O(n). Обратное чтение односвязного списка использует O(n) временной памяти для массива значений. У двусвязного списка обход требует O(1) памяти, но возвращаемая строка результата занимает O(n). Новому узлу нужна O(1) память.

### 4.3. Стек и очередь

| Операции | Время | Дополнительная память |
|---|---|---|
| `SCREATE`, `QCREATE` | O(1) | O(1) |
| `SPUSH`, `QPUSH`, одно значение | O(1) | O(1) |
| `SPOP`, `QPOP` | O(1) | O(1) |
| `SREAD`, `QREAD`, `PRINT` | O(n) | O(n) для строки вывода |

### 4.4. Дерево

| Операции | Время | Дополнительная память |
|---|---|---|
| `TCREATE` | O(1) | O(1) |
| `TINSERT`, одно значение | O(n) | O(n) для BFS-очереди |
| `TFIND`, `TGET`, `ISMEMBER` | O(n), лучший случай O(1) | O(n) |
| `TCHECKCOMPLETE` | O(n) | O(n) |
| `TREAD` | O(n) | O(n) |
| `PRINT` с текстовыми путями | O(n log n) для Complete-дерева | до O(n log n) для очереди путей |

Вставка здесь намеренно реализована простым BFS, как учебный алгоритм. Высота Complete-дерева равна O(log n), но поиск первой свободной позиции обходом в ширину требует O(n). Построение n узлов последовательными вставками, в том числе загрузка дерева из файла, требует O(n²). Возможное улучшение для защиты — хранить количество узлов и определять путь к позиции n+1 по битам индекса, что даёт O(log n) на вставку. В текущую реализацию это улучшение не включено.

Пути вида `root->left->right` имеют длину O(log n), поэтому вывод всех таких путей учитывает O(n log n) символов. Обычное чтение дерева возвращает только значения и остаётся O(n).

### 4.5. Полная стоимость запроса

Для C++ поиск имени в `std::map` занимает O(log m), где m — число контейнеров; для Go-map ожидаемое время O(1). Перед каждым запросом читается весь файл. Для линейных структур загрузка линейна по числу элементов; для дерева из n элементов — O(n²) из-за последовательных BFS-вставок. Сохранение линейно по общему объёму данных.

Таким образом, команда `SPOP` имеет O(1) как операция стека, но полное выполнение программы с загрузкой и сохранением не имеет O(1). Несколько значений в запросе требуют нескольких операций: например, k последовательных BFS-вставок в дерево размера n дают O(kn + k²).

## 5. Достоинства, недостатки и применение

| Структура | Достоинства | Недостатки | Применение |
|---|---|---|---|
| Массив | Быстрый доступ по индексу, компактное расположение | Сдвиги при вставке в середину, резерв памяти | Таблицы, последовательности с частым индексным доступом |
| Односвязный список | Простое изменение головы, по одной ссылке на узел | Нет движения назад, линейный поиск и удаление хвоста | Цепочки задач, реализация стека |
| Двусвязный список | Движение в обе стороны, O(1) изменения концов | Две ссылки на узел, линейный поиск по значению | История переходов, двусторонние очереди |
| Стек | Простой LIFO-интерфейс, O(1) push/pop | Доступ преимущественно к вершине | Отмена действий, разбор выражений, DFS |
| Очередь | FIFO-порядок, O(1) добавление и извлечение | Нет быстрого произвольного доступа | Очереди заявок, BFS, буферизация |
| Complete Binary Tree | Логарифмическая высота, заполнение без пропусков | Нет упорядочивания значений, линейный поиск и BFS-вставка | Основа формы двоичной кучи; для кучи дополнительно нужно свойство порядка |

## 6. Контрольные примеры и визуальные формы

### 6.1. Дерево варианта 3

Запрос:

```sh
./dbms --file control.data --query 'TINSERT mytree 10 5 20 3 7 15'
```

Получается дерево:

```text
            10
          /    \
         5      20
        / \     /
       3   7   15
```

Последний уровень заполнен слева направо; отсутствует только правый ребёнок узла 20. Это Complete-дерево. Оно не Full: у узла 20 один ребёнок. Различие принципиально для варианта 3.

Фактический вывод `PRINT mytree`:

```text
=== PRINT mytree ===
root = 10
root->left = 5
root->right = 20
root->left->left = 3
root->left->right = 7
root->right->left = 15
```

`TREAD mytree` выводит `10 5 20 3 7 15`, `TCHECKCOMPLETE mytree` — `TRUE`, `TFIND mytree 7` — `TRUE`, `TFIND mytree 100` — `FALSE`.

После вставки `20 -2`:

```text
            10
          /    \
         5      20
        / \    / \
       3   7  15 20
      /
    -2
```

Проверка по-прежнему возвращает `TRUE`. Повтор значения 20 не удаляется и занимает отдельный узел.

Отрицательные примеры для тестирования функции проверки:

```text
  1                 1
   \               / \
    2             2   3
                     /
                    4
```

Слева есть правый ребёнок без левого. Справа после свободных позиций у узла 2 находится занятая позиция под узлом 3. Оба дерева не Complete. Эти формы создаются напрямую в модульных тестах, поскольку штатная вставка сохраняет Complete и не создаёт пропусков.

### 6.2. Массив

```text
MPUSH a one two three       [one, two, three]
MPUSHIDX a 1 middle         [one, middle, two, three]
MSETIDX a 0 zero            [zero, middle, two, three]
MDELIDX a 2                 [zero, middle, three]
MGET a 1                   middle
MLENGTH a                  3
```

### 6.3. Списки

Одинаковая последовательность для F и L:

```text
XPUSH list b d             b -> d
XPUSHHEAD list a           a -> b -> d
XPUSHBEFORE list d c       a -> b -> c -> d
XPUSHAFTER list d e        a -> b -> c -> d -> e
XREADTH list               e d c b a
XPOPBEFORE list c          a -> c -> d -> e
XPOPAFTER list c           a -> c -> e
XPOPHEAD list              c -> e
XPOP list                  c
XDELVAL list c             пусто
```

Для двусвязного списка каждая связь дополнительно имеет обратное направление. `X` заменяется на F или L.

### 6.4. Стек и очередь

```text
SPUSH s 1 2 3        вершина -> [3] -> [2] -> [1] <- основание
SREAD s              3 2 1
SPOP s               3
SPOP s               2
SPOP s               1

QPUSH q 1 2 3        голова -> [1] -> [2] -> [3] <- хвост
QREAD q              1 2 3
QPOP q               1
QPOP q               2
QPOP q               3
```

Каждая строка запроса выполняется отдельным запуском программы. Поэтому эти примеры также подтверждают сохранение LIFO/FIFO после перезагрузки файла.

### 6.5. Ошибки и границы

Проверены пустые контейнеры, один элемент, вставка в индекс длины, отрицательный индекс, выход за границу, неизвестная команда, неверное число аргументов, нечисловое значение дерева, переполнение 32-битного числа, повтор имени и конфликт типов. Для ошибочных запросов проверяется ненулевой код завершения и побайтовая неизменность файла.

Случайные последовательности операций двух списков сравниваются с эталонным списком Python после каждого изменения в прямом и обратном порядке. Это проверяет ссылки после удаления головы, хвоста и внутренних узлов, включая повторяющиеся значения.

Фактические результаты сборки и тестов приведены в `TEST_RESULTS.md`; полный контрольный запуск — в `examples/control_output.txt`.

## 7. Вывод

Реализованы шесть типов структур данных, командный интерфейс и файловое хранение. Для варианта 3 реализовано Complete Binary Tree с добавлением, поиском, чтением и проверкой полноты. Операции проверены на обычных данных, граничных случаях и ошибочных запросах. Определены сложности структурных операций и отдельно рассмотрены затраты файлового интерфейса.

## 8. Подготовка к защите

- Complete задаёт заполнение уровней слева направо; Full требует у каждого узла 0 или 2 детей. Это разные свойства.
- Вставка сравнивает позиции, а не значения. Отсортированность не поддерживается.
- Логарифмическая высота не даёт логарифмический поиск по произвольному значению.
- Пропуск при BFS запрещает все последующие непустые позиции.
- `SPOP` меняет вершину, `QPOP` — голову; оба возвращают извлечённый элемент.
- Поиск узла по значению может занимать O(n), даже если изменение его ссылок стоит O(1).
- Для расширения можно добавить подсчёт узлов, высоту, обходы preorder/inorder/postorder или оптимизировать вставку по двоичному индексу. При добавлении изменяющей команды нужно обновить интерфейс, сохранение и тесты.
